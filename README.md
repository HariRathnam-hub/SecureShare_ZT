# SecureShare ZT

A **Zero Trust secure file exchange platform**. It is not a Drive clone: the point is *governed* access.
Every request proves identity, every file carries a classification and policy, and every action is audited.

Stack: React + Vite + TypeScript + Tailwind + React Query + Zustand (frontend); Node + Express + TypeScript + MongoDB (backend).
Storage is pluggable and defaults to local disk. Email goes through the Brevo API. No cloud storage credentials are needed to run.

## Run locally (Windows PowerShell)
Prerequisites: Node.js 20+ (`node -v`) and a MongoDB Atlas connection string.

```powershell
# 1. Backend  (terminal 1)
cd backend
Copy-Item .env.example .env          # then: notepad .env  -> set MONGODB_URI and two DIFFERENT JWT secrets
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"   # run twice for the two secrets
npm install
npm run dev                          # http://localhost:5000
npm run seed:admin                   # optional: set ADMIN_EMAIL / ADMIN_PASSWORD in .env first
npm test                             # unit + boot tests, no database needed

# 2. Frontend  (terminal 2)
cd frontend
npm install
npm run dev                          # http://localhost:5173  (proxies /api to the backend)
```
macOS/Linux: use `cp .env.example .env` instead of `Copy-Item`. Type checks and builds: `npm run typecheck` / `npm run build` in each folder.
Without `BREVO_API_KEY`, verification and reset links are printed in the backend console (development only).

## Storage layer
`src/storage/` defines `StorageProvider` (`uploadFile`, `downloadFile`, `deleteFile`, `getMetadata`, optional `healthCheck`).
All file code uses it through `getStorage()`. `LocalStorageProvider` writes to `UPLOAD_DIR` with:
- keys generated by the server only, validated against traversal (`..`, absolute paths, odd characters);
- atomic writes (temp file + rename), `0600` files and `0700` directories;
- startup probe: the server refuses to boot if the directory isn't writable.

To add a backend later, implement the interface and call `registerStorageProvider('name', () => new MyProvider())`.

**Deployment warning:** local disk is per-instance. On Render the filesystem is ephemeral, so attach a *persistent disk*
(e.g. mount `/var/data`, set `UPLOAD_DIR=/var/data/uploads`) and run a single instance, or add a shared-storage provider before scaling out.

Download integrity: each version's SHA-256 is recorded at upload and re-verified on every download. A mismatch blocks the download and is audited.

## Zero Trust controls
| Classification | Who can access | Per-download purpose + reason | Links | Rooms |
|---|---|---|---|---|
| public | any signed-in user | no | yes | yes |
| internal | owner, explicit grant, room member | no | yes | yes |
| confidential | owner, explicit grant, room member | **required** | password + 7-day max | yes |
| restricted | owner, or a grant created by an **approved access request** (max 7 days) | **required** | never | never |

- **Purpose-based access:** `purpose` (project, research, audit, compliance, education, other) and a free-text `reason` (10+ chars) are stored on the `AccessRequest`, repeated in the approval audit record, and recorded on every confidential/restricted download. Missing purpose returns HTTP 428.
- **Time lock:** `availableFrom` / `availableUntil` (either may be empty). Outside the window every non-owner download is denied, including via links. The owner is exempt so they can always manage their file. Metadata remains visible.
- **Secure links:** always expire (1 minute to 30 days), optional password (5 wrong attempts disables the link), download limit, single-use (`maxDownloads = 1`, consumed atomically so concurrent redemptions can't both win). Only a hash of the token is stored; the token travels in a POST body, not the URL. Redeemers must sign in so redemption is attributable.
- **Data rooms:** owner + members with roles (viewer / editor / manager), room policy (viewers may download, highest classification accepted), and a room audit log.
- **Watermark:** PDFs downloaded by non-owners get a diagonal tag and footer (user, time, IP, download ID). Other file types are audited with `watermark.applied=false`. A PDF that cannot be watermarked is blocked, not served raw.
- **Audit log:** append-only model (mutations throw). Records uploads, downloads, deletions, shares, links, requests, approvals, rejections, room changes, every `ACCESS_DENIED`, sign-ins, failed logins, session revocations and every adaptive `POLICY_DECISION`. The audit write happens *before* bytes are returned, so no record means no download.
- **Re-check on every download:** `authorizeDownload()` (`files/download-policy.service.ts`) runs inside `deliverFile`, so it covers direct downloads and link redemptions. It re-reads the user (still active?) and the file, then re-runs the existing `evaluateFileAccess` / `evaluateLinkAccess` (ownership, classification, grants, room membership, time window), re-requires purpose + reason, and only then asks the adaptive policy. A ban, revoked share, lapsed grant, reclassification or closed time window that happened mid-request still stops the download.
- **Least privilege:** the admin role can manage users and read the platform audit trail but has no access to file contents.

## Phase 3: Cloudflare Tunnel, Cloudflare Access, adaptive policy, security dashboard

### 1. Share a demo with a Cloudflare Quick Tunnel (no domain, no account)
A Quick Tunnel gives your local app a temporary public `https://<random>.trycloudflare.com` URL. **The URL changes every time you start it, has no uptime guarantee, and is for demos and testing only, not production.** A Quick Tunnel does **not** enable Cloudflare Access or any other Cloudflare protection: anyone who has the URL can reach the sign-in page, and the app's own authentication is the only gate.

Only the **frontend** port is exposed. The browser calls `/api` on the same origin and the Vite server forwards it to the backend on `localhost:5000`, so the backend port, the database credentials and every secret stay on your machine, and the refresh cookie stays same-origin.

```powershell
# One-time: install cloudflared (then close and reopen PowerShell so it is on PATH)
winget install --id Cloudflare.cloudflared
cloudflared --version
# No winget? Download cloudflared-windows-amd64.exe from https://github.com/cloudflare/cloudflared/releases and run it from its folder.
```

```powershell
# Terminal 1: backend              Terminal 2: frontend
cd backend; npm run dev            cd frontend; npm run dev
# Terminal 3: the tunnel (points at the FRONTEND port)
cloudflared tunnel --url http://localhost:5173
```
`cloudflared` prints a line like `https://quiet-river-1234.trycloudflare.com`. Put that URL into `backend/.env`, then **restart the backend** (Ctrl+C, `npm run dev`):

```ini
CLIENT_URL=https://quiet-river-1234.trycloudflare.com      # CORS + the links inside verification/reset emails
ALLOWED_ORIGINS=http://localhost:5173                       # keeps localhost working too
TUNNEL_PUBLIC_URL=https://quiet-river-1234.trycloudflare.com # informational, shown on the Security page
TRUST_PROXY_HOPS=2                                          # cloudflared -> Vite -> API, so req.ip is the real client
```
Leave `frontend/.env` with `VITE_API_URL=` empty. Open the tunnel URL in a browser. Repeat the `.env` edit whenever you start a new tunnel. Origins must match exactly (scheme + host, no trailing slash); any other origin is rejected by CORS.

Tips: `npm run dev` works through the tunnel, but a build is steadier for a demo: `cd frontend; npm run build; npm run preview` (same port, same proxy). Vite only accepts `*.trycloudflare.com` Host headers by default (see `vite.config.ts`); for a named hostname set `$env:VITE_ALLOWED_HOST="app.example.com"` before starting it.
If audit entries show `127.0.0.1` as the IP, lower or raise `TRUST_PROXY_HOPS`. IP addresses appear in audit records and PDF watermarks for context only; no access decision relies on an IP address.

Exposing the backend with a second tunnel (`cloudflared tunnel --url http://localhost:5000`) is not recommended and not supported in development mode: the refresh cookie is `SameSite=Lax` outside production, so a separate API origin would break sign-in persistence.

### 2. Cloudflare Access (optional identity layer)
**What the code does.** With `CLOUDFLARE_ACCESS_ENABLED=true`, every `/api/v1` request must carry a `Cf-Access-Jwt-Assertion` header that verifies against the public keys Cloudflare publishes at `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`: RS256 signature, issuer (`https://<team>.cloudflareaccess.com`), audience (your AUD tag) and expiry (a token with no `exp` is rejected). Keys are fetched from the configured team domain only (never from the token), cached for an hour and refetched when Cloudflare rotates them. The `Cf-Access-Authenticated-User-Email` header is never trusted. Requests without a valid assertion get `401`; if the keys cannot be fetched and none are cached the request is refused with `503` (fail closed). The verified identity is attached to the request and recorded on download policy decisions. The app's own sign-in (JWT + refresh cookie) still applies on top: Access is an additional layer, not a replacement. With Access disabled (the default) nothing changes.

**Why a Quick Tunnel cannot do this.** Access protects a hostname inside *your* Cloudflare account. `*.trycloudflare.com` hostnames belong to Cloudflare's Quick Tunnel service, so you cannot attach an Access application to them. Turning the flag on while using a Quick Tunnel would only lock you out, because no assertion would ever arrive. Until Access is configured and verified, nothing in this project claims it is active.

**Free-tier path (needs a hostname you control).** The Zero Trust Free plan has been available at no cost for small teams, but Access in front of an app needs a hostname on a domain that is added to your Cloudflare account. A domain costs a few dollars per year at any registrar (Cloudflare Registrar sells at cost); there is no purchase-free way to put Access in front of a Quick Tunnel. Dashboard labels change over time, so treat the steps below as a guide and check Cloudflare's current documentation.

Dashboard steps (these cannot be automated by this repository):
1. Create a free Cloudflare account and add your domain (change its nameservers as instructed).
2. Open **Zero Trust** (one.dash.cloudflare.com), pick a team name and the Free plan. Your team domain is `<team>.cloudflareaccess.com`.
3. **Networks → Tunnels → Create a tunnel** (Cloudflared). Install the connector on this PC with the command the dashboard shows (Windows tab, run in PowerShell as shown) and add a **public hostname**, e.g. `app.yourdomain.com` → `http://localhost:5173`.
4. **Access → Applications → Add an application → Self-hosted.** Hostname `app.yourdomain.com`. Add a policy: action **Allow**, include **Emails** (or an email domain) for the people who may enter, plus an identity provider such as One-time PIN.
5. Open the application's overview and copy its **Application Audience (AUD) Tag**.
6. Edit `backend/.env`, then restart the backend:
```ini
CLIENT_URL=https://app.yourdomain.com
CLOUDFLARE_ACCESS_ENABLED=true
CF_ACCESS_TEAM_DOMAIN=yourteam.cloudflareaccess.com
CF_ACCESS_AUD=<paste the AUD tag>
TRUST_PROXY_HOPS=2
TUNNEL_PUBLIC_URL=https://app.yourdomain.com
```
7. Verify: browse to `https://app.yourdomain.com` (Cloudflare shows its login first), sign in to the app, then open **Security**; "Assertions verified" should be above zero. Calling the API directly (`curl http://localhost:5000/api/v1/files`) must return `401 Cloudflare Access verification required`. Only treat Access as active after both checks pass.

Keep `CLOUDFLARE_ACCESS_ENABLED=false` for plain `localhost` development: with it on, every API call needs the assertion, which only exists behind Cloudflare.

### 3. Adaptive Zero Trust file policies
Runs inside every download (direct and link) after the existing rules, never instead of them: classification, grants, room membership, time lock, purpose + reason and the restricted-file approval rule are unchanged. Result: `ALLOW`, `REQUIRE_APPROVAL` or `DENY`, written to the audit log as `POLICY_DECISION` (decision, reason, score, factors, classification, access path, verified Access email if any) before any bytes are read. If that audit write fails, no bytes are served.

Signals (all from data the platform already records; `security/policy.ts` holds every number):

| Signal | Source | Points |
|---|---|---|
| Revoked / signed-out session (no live refresh token) | `User.refreshTokens` | 50 and always `DENY` |
| 3+ / 5+ failed logins for the account in 6 h | `LOGIN_FAILED` audit events | 20 / 40 |
| 15+ / 30+ downloads in the last hour | `DOWNLOAD_FILE` audit events | 25 / 45 |
| New device: user-agent never used by this account (live sessions or earlier `LOGIN_SUCCESS`) | refresh tokens + audit | 20 |

Level: below 30 low, 30 to 59 medium, 60 and above high.

| Level | public / internal | confidential / restricted |
|---|---|---|
| low | ALLOW | ALLOW |
| medium | ALLOW | REQUIRE_APPROVAL |
| high | REQUIRE_APPROVAL | DENY |

`REQUIRE_APPROVAL` is satisfied by an unexpired grant that came from an **approved access request** (the owner's explicit decision). Otherwise the user sees a prompt to send an access request (this works even if they already have access, because the request flow now accepts it while approval is required), and the owner approves it under Access requests. Owners are never asked to approve their own files. For restricted files every grant already comes from an approved request, so the table effectively means: elevated risk is tolerated on restricted files (the approval is on file) until it reaches high, where they are denied.

Limits to be aware of: the "new device" signal is the user-agent string, which is trivially spoofable, so it only adds points and can never deny on its own. Nothing is derived from IP addresses or browser fingerprints. Failures of the policy checks themselves fail **closed for restricted files** (`DENY`); for other classifications the download proceeds and the failure is logged. Tune or disable signals by editing `RISK` in `src/security/policy.ts`.

New audit actions: `LOGIN_SUCCESS`, `LOGIN_FAILED` (unknown emails are grouped by a hash, never stored), `SESSION_REVOKED` (refresh-token reuse, password reset), `POLICY_DECISION`. New target types: `user`, `system`. Existing records are unaffected.

### 4. Security dashboard
Admins get **Security** in the sidebar (`/admin/security`, API `GET /api/v1/security/overview`, admin-only, built from the audit log). It shows Access enabled/disabled and configured/unconfigured with verified/rejected counters since the last server start, tunnel status (**manually configured** only when `TUNNEL_PUBLIC_URL` is set; the server cannot detect a running tunnel), allow / approval / deny counts, failed logins, downloads, access requests, and recent events for each.

### What needs the Cloudflare dashboard or your own accounts
Creating the Cloudflare account and Zero Trust team, adding a domain, creating the named tunnel and public hostname, creating the Access application and Allow policy, and copying the AUD tag. Code cannot do these. Quick Tunnel itself needs only the `cloudflared` binary.

### Verification status
Automated here: type checks, backend build, unit and boot tests (`npm test`), including Access verification against locally generated RSA keys with a stubbed key endpoint, the policy decision table, the per-download re-check with stubbed models, CORS origins and env validation. **Not exercised:** a real Cloudflare Access application, a live Quick Tunnel, and a real MongoDB (no network access when this was built), so test those once on your machine.

## Security hardening (Turnstile, rate limits, file access, WAF)

Cloudflare Turnstile on login/register/password reset, per-purpose rate limits (HTTP 429 + `Retry-After`, optional shared MongoDB store),
hardened uploads/downloads, a production-only CORS lock-down, and an honest account of what Cloudflare WAF can and cannot protect for
`pages.dev` + Render: see [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md). New variables: `TURNSTILE_SECRET_KEY` (backend, required in
production), `VITE_TURNSTILE_SITE_KEY` (frontend), `RATE_LIMIT_STORE`, `CLIENT_IP_HEADER`, `ORIGIN_VERIFY_SECRET`. Deploy the frontend first, then the backend.

## Migrating an existing database
If you ran the earlier build (R2 + `accessWindow`), run once: `npm run migrate:phase2-refactor`.
It renames `accessWindow` to `availableFrom`/`availableUntil` and `r2Key` to `storageKey`.
**Objects already in R2 are not copied to local disk**; export them first if they matter.

## Deploy
- **Render (API):** build `npm install --include=dev && npm run build`, start `npm start`. Set every required variable, `NODE_ENV=production`, `CLIENT_URL` = your Vercel URL, and attach a persistent disk for `UPLOAD_DIR`.
- **Vercel (web):** set `VITE_API_URL=https://<service>.onrender.com/api/v1`. `vercel.json` handles SPA rewrites.
- **Secrets:** never commit `.env`. Rotate any key that has been shared outside your secret manager.
